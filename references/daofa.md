# 道 + 法 — 底层判断与协作组织

## 道 · 三个底层判断（决定结果上限）

1. **以边界换聚焦**：不给边界，Codex 就只能平均用力；明确不做什么、什么可妥协、什么不能妥协，结果才会真正聚焦。
2. **以信息换准确**：你提供的信息密度，决定结果和预期的贴合度；目标、背景、约束和细节说得越清楚，返工越少。
3. **以文档和验证换稳定**：上下文会衰减，口头共识会丢失；目标、方案、进度要尽早落文档并持续更新，结果还要靠测试或验证闭环来证明。

> 应用：接到模糊任务时，先用这三句话逼出边界、信息、验证方式，再进入具体动作。

## 法 · 七条组织原则

| # | 原则 | 说明 |
|---|------|------|
| 01 | 先收敛，再展开 | 目标、边界、路径不清时，先收敛问题。 |
| 02 | 明确任务的时间尺度 | 长期建设、阶段性过渡、短期止血，是三种不同任务，方案选择标准也不同。 |
| 03 | 根据阶段定模式 | 方案期适合讨论和计划，问题模糊时适合先诊断，修 bug 适合先复现，主线清晰后再进入执行，阶段结束后再独立复查。 |
| 04 | 用结构化表达降低偏差 | 尽量把请求组织成稳定结构，让目标、约束、输出和验证标准都清楚可读。 |
| 05 | 用文档沉淀阶段共识 | 多轮协作不要只靠会话记忆，目标、方案、决策、进度和风险要尽早外化并持续更新。 |
| 06 | 用验证闭环约束结果 | 不要只停在"已经改了"，要用测试、验收标准或最小验证步骤确认结果真的成立。 |
| 07 | 兜底方案必须显式确认 | 采用临时解前先说明更优路径为何暂不可行；实施前确认，实施后再验证并说明风险与回收方式。 |

## 法 · 最小闭环（五段式，贯穿全书）

在单次任务里，七条原则通常可压缩成一条链：

**目标 → 模式 → 约束 → 输出 → 验证**

它的价值不在格式本身，而在于提前说清偏差最容易出现的地方。

### 通用推荐骨架（可直接套用）

```
目标：解决【具体问题】；如果适合，尽量逼近【最终可用状态】。
模式：【直接推进 / 先诊断 / 先复现 / 先收敛计划】。
约束：这次只解决【范围 A】，不扩展到【范围 B】；这次任务属于【长期建设 / 阶段性过渡 / 短期止血】，优先【长期可维护 / 短期可交付】。
输出：先给【判断 / 方案 / 完整计划】，再【落地 / 继续问关键问题】。
验证：通过【测试 / 最小验证步骤 / 验收标准】证明结果有效。
```

> 用法：把下面的骨架当作每次给 AI 的"请求外壳"，再叠加 `shu.md` 里的局面打法或 `qi.md` 里的组合模板。
